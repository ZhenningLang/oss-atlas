# REQUIREMENT: oss-atlas quality and health remediation

## Goal

Raise the whole oss-atlas index to high selection quality by combining mechanism fixes, batch rewriting, health rescoring, and mandatory reviewer gates after each batch.

## Problem

The current index was partly generated by weak models. Several pages have weak or templated project introductions, especially in `Comparison`; health radar scores also contain too many `?` axes and some pages show drift between frontmatter health data, generated SVG cards, and prose in `Health & viability`.

## Scope

In scope:

- Run a whole-repo content and health audit.
- Improve deterministic quality scans and/or lint tests for known bad patterns.
- Fix health scoring mechanisms where `?` comes from tool weakness rather than genuinely unavailable evidence.
- Refresh upstream snapshots where placeholder values break stale-check reliability.
- Re-score health and regenerate radar SVGs in batches.
- Rewrite project pages in batches, preserving strong existing content and replacing weak or stale sections.
- Keep English canonical pages and Chinese mirror pages aligned.
- After every batch, run an explicit reviewer phase to classify issues as mechanism defects, generation/prompt defects, fact-source gaps, or one-off mistakes.
- If reviewer finds mechanism defects, stop batch expansion and fix the mechanism before continuing.
- Continue until the intended project pages are high quality across the index.

Out of scope:

- Do not turn oss-atlas into a database, search engine, or embedding system.
- Do not fabricate health scores to reduce `?`.
- Do not overwrite strong `When NOT to use` sections just for uniformity.
- Do not push, deploy, or change remote state.

## Initial Baseline

As of 2026-07-04 local audit:

- 295 English project pages and 295 Chinese project pages.
- 59 category nodes.
- All English pages have a `health:` block.
- `overall: ?` appears on 1 English page.
- Placeholder zero `default_branch_sha` appears on 64 English pages.
- Unknown health axes on English pages:
  - `responsiveness`: 150
  - `adoption`: 127
  - `governance`: 59
  - `risk_license`: 15
  - `maintenance`: 0
  - `longevity`: 0
- `make lint` baseline: 0 errors, 8 warnings.
- `make test` baseline: 17 tests OK.

## Quality Requirements

A high-quality project page must satisfy:

- `When to use` is a concrete second-person user story, not a feature dump.
- `When NOT to use` contains real negative-space selection filters.
- `Comparison` names real substitutes, marks indexed/not-indexed status correctly, and gives a decisive tradeoff.
- No obvious truncation, placeholder prose, or generic template wording.
- Health frontmatter, embedded SVG card, and `Health & viability` prose agree.
- Remaining `?` health axes have a clear reason and are reflected in prose or Caveats when decision-relevant.
- Caveats list every material unverified or inferred claim.
- Chinese pages are monolingual mirrors and link to `.zh.md` siblings where available.
- README, INDEX, and category routes remain structurally valid.

## Batch Workflow

Each batch must follow this loop:

1. Select a small risk-prioritized batch.
2. Verify decisive facts from source material where needed.
3. Rewrite or repair English and Chinese project pages.
4. Recompute health/upstream/card data where applicable.
5. Run validation commands.
6. Run reviewer phase.
7. Classify every reviewer finding by root cause.
8. If the root cause is mechanism-level, fix tools/prompts/scans/tests before expanding to the next batch.
9. If the root cause is one-off, rework the affected pages and rerun validation.

## Suggested Phase Plan

Phase 1: Audit and quality gates

- Add deterministic quality scan coverage for known bad patterns:
  - templated comparison prose such as `Use this page for its stated niche` and `当前页用于它的主场景`;
  - truncation fragments such as `trac.`, `(Node.`, `and.`, `per-har.`, `before co.`;
  - `.zh.md` pages linking to `.md` pages where a `.zh.md` sibling exists;
  - comparison rows marked `未收录` / `not indexed` while linking to an existing indexed page;
  - health prose drift from frontmatter where detectable.
- Produce a whole-repo audit report.

Phase 2: Health mechanism fixes

- Make GitHub CLI lookup portable instead of hard-coding `/opt/homebrew/bin/gh`.
- Fix or improve responsiveness PR fallback if it lacks required GraphQL fields.
- Review adoption scoring for registry-less tools and structural no-package cases.
- Improve diagnostics for `?` axes so reviewers can distinguish tool weakness from genuine unknowns.
- Add tests for changed scoring behavior.

Phase 3: Upstream and health consistency

- Repair placeholder zero upstream SHAs in small batches.
- Ensure health frontmatter, SVG cards, and prose stay synchronized.
- Add validation or scan coverage for obvious health/prose drift.

Phase 4: Batch content remediation

- Start with the known high-risk sample batch:
  - n8n
  - PRAW
  - Selenium
  - PDF.js
  - youtube-dl
  - karpathy-skills
  - Open Design
  - Grafana
- Then proceed category/risk batches until all intended pages pass review.

Phase 5: Whole-index closeout

- Run full structural validation and tests.
- Compare final `?` axis distribution against baseline.
- Run holdout reviewer sampling over pages not manually focused earlier.
- Produce final summary with remaining risks and any intentionally retained unknowns.

## Validation Commands

Minimum validation after every implementation phase:

```bash
make lint
make test
```

Additional validation depends on phase:

- quality scan command, once added;
- health dry-run or targeted `make health PAGE=...` for rescored pages;
- git diff review for content and generated SVG changes.

## Reviewer Gate

Every batch reviewer must output:

- PASS / REWORK / STOP_AND_FIX_MECHANISM.
- Findings with file path, evidence, severity, and root cause.
- Whether the issue came from mechanism, prompt/generation, source-data limits, or one-off execution.
- Required action before the next batch.

If the same class of issue appears more than once in a batch, treat it as mechanism-level until proven otherwise.
